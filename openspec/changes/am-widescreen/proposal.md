# Change: Auto Modellista widescreen (Hor+ and the HUD at the edges)

## Why

The user asked on 2026-11-04 for Hor+ widescreen and HUD alignment in
Auto Modellista, the way BLiNX 2 has them. At 4:3 the game draws
the course and its HUD in a 640x480 frame. The toolkit's Hor+
(`display.aspect`, archived 2026-10-30 as enhancements-hor-plus, with the
fullscreen-fx, sea-fan and draw-merge follow-ups) widens the projection and
keeps 2D in the 4:3 columns. So with Hor+ alone the race HUD (speed, gear,
position, lap times, the course map) sits in the middle of a wide screen.
The user's rule (2026-10-18) is that a centred HUD is not a feature: the
HUD must look right at every aspect.

## Native widescreen or Hor+

The toolkit's other route, `display.widescreen = native` (cat
`native-widescreen`, still a spec), is for titles that have their own 16:9
mode, chosen through the dashboard's widescreen flag (XC_VIDEO,
`XGetVideoFlags`). Auto Modellista has no such mode (design D1):

- its one `XGetVideoFlags` call (sub_00179A1B, from sub_000F7C60 at boot)
  passes the widescreen bit to the present parameters and stores a 16/9
  float at 0x4330F4, which no code reads;
- every projection the game builds uses a 4/3 aspect constant;
- the toolkit answers XC_VIDEO in the wrong domain, so every game sees 0
  today, and native mode is not built yet.

So this change uses Hor+ (`display.aspect`). Native mode would bring
nothing the game does not already lack.

## What changes

- **Hook slots** (`game.toml` `[mods]`): the twelve entries of the game's 2D
  library (0x10E180..0x10E6F0) and the lap times' digit helper
  (0x22B20, the table's wrapper), with `no_st0`.
  `config/hook_functions.json` is generated by `analyze`.
- **The frame glue** (`src/recomp_manual.c`): `xbox_mod_frame()` after the
  XDK's `D3DDevice_Swap` (sub_002077A0), as KUF has it. The mod API counts
  guest frames there and hands the mods guest memory. The game had no such
  call.
- **A `hud` mod** (`src/hud_mod.c`, the game's first mod, registered in
  `src/main.c`): for each 2D entry it builds a quad from the command struct
  in the mod's guest block, hands it to the toolkit's HUD layer, writes the
  result back into the struct, and puts the struct back after the draw
  (design D2, D3). One call draws pieces on both sides; the mod mirrors
  its right ones through the layer (design D5). On by default as BLiNX 2's and KUF's; it acts only at a
  wide `display.aspect`, so stock 4:3 is unchanged.
- **`config/hud.toml`**, embedded at build time: the canvas (640x480,
  top-left), the layout of the mod's quad, the groups and one row per call
  site, from a level-1 capture (design D4). The menus stay unlisted
  (centred, as at 4:3), and so does the gauge cluster: the tachometer is a
  3D model the layer cannot move (design D6, a toolkit follow-up).
- **Docs and defaults**: `docs/env.md` (`RECOMP_HUD` and the toolkit keys
  the mod reads), `packaging/config.default.toml` (`display.hud_aspect`,
  `display.hud_margin`, `mods."hud.enable"`), `scripts/test_hud_table.py`.

No toolkit change is needed: the layer's mod API (v6: `hud_apply`,
`guest_alloc`) covers immediate-mode 2D once the mod builds the vertices.

- **`CHANGELOG.md`**: the widescreen entry under Unreleased.

## Pass bar

- At 16:9 the race HUD's 2D (position, lap times, lap count, course map)
  sits at the frame's edges, the gauge cluster stays whole beside the
  middle, the menus render as at 4:3, and nothing is cut at the 4:3
  columns.
- At 4:3, and with the mod off, the frames match the build of main
  (5cb9949) on the same toolkit.
- D3D11 (the PC) is the reference; Metal agrees or the gap is recorded.
